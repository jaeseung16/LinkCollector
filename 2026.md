## LinkPiler Update Plans

Investigated against the current state of the repo (Xcode 26.6 installed; app target `LinkPiler`
at `IPHONEOS_DEPLOYMENT_TARGET 18.0` / `MACOSX_DEPLOYMENT_TARGET 15.0`, Swift 5.0 language mode,
version 1.6 build 51; active Core Data model is `LinkCollector 2.xcdatamodel`, CloudKit-backed,
two entities `LinkEntity`/`TagEntity`; persistence goes through the external package
[PersistenceSwift](https://github.com/jaeseung16/PersistenceSwift) 0.2.15, shared with other apps
and consumed by three targets: `LinkPiler`, `LinkPilerShareExtension` (+ Mac variant),
`LinkPilerWidgetExtension`).

Housekeeping note (not part of the three points, but noticed along the way): `ShareExtension/`,
`LinkCollectorExtension/`, `LinkCollectorSafariExtension/`, `LinkPiler2/`, and
`LinkCollector.xcodeproj` (which has no `project.pbxproj`, just an empty workspace stub) are not
referenced by the live `LinkPiler.xcodeproj`. They look like leftovers from an earlier project
layout — worth deleting in a separate cleanup pass so they don't get mistaken for live targets.
Also: the project-level default build settings still say `IPHONEOS_DEPLOYMENT_TARGET = 15.0`
(every actual target overrides it to 18.0) — harmless but worth aligning when the deployment
target is bumped for Liquid Glass.

### Recommended sequence

1. **Toolchain/deployment bump** (prerequisite for #1 and #3 below)
2. **Liquid Glass UI pass + icon**
3. **Apple Intelligence summarization** (adds the schema change while the model is still simple)
4. **Swift 6 language mode + concurrency cleanup** — do this *before* SwiftData (#5), not after:
   flipping language modes is far easier to isolate and verify when the persistence layer hasn't
   also just changed underneath it.
5. **SwiftData migration** (last — no user-visible payoff, widest blast radius, easiest to validate
   once the schema and language mode are both settled)

### 1. Adopting Liquid Glass

**Status: done** (2026-08-22). Deployment targets are at 26.0 across all four targets, the
Icon Composer asset `LinkCollector/AppIcon_iOS26.icon` ships as `ASSETCATALOG_COMPILER_APPICON_NAME`,
and the container/cleanup items below have all been applied. No `UIDesignRequiresCompatibility`
opt-out key is set anywhere, so the SDK-level Liquid Glass adoption is live.

**Prerequisite:** Liquid Glass APIs and the auto-adoption that comes from compiling against the
iOS 26 SDK both require raising `IPHONEOS_DEPLOYMENT_TARGET` (and `MACOSX_DEPLOYMENT_TARGET`) to
26.0 across the `LinkPiler`, `LinkPilerShareExtension`, `LinkPilerShareExtensionMac`, and
`LinkPilerWidgetExtension` targets. Xcode 26.6 is already installed, so this is a project-settings
change, not a toolchain install. Apple documents an Info.plist opt-out key for staging the visual
change independently of the SDK bump — confirm the exact key name in Apple's Liquid Glass
migration notes before relying on it, since I'm not fully certain of it from memory.

**App icon.** `Assets.xcassets/AppIcon.appiconset` currently holds only flat, pre-rendered PNGs
("Artboard 1.png", etc.) — there is no layered/vector source in the repo. iOS 26's light / dark /
clear / tinted icon variants are generated from a layered source via Icon Composer. No such source
file exists here, so this item is really two different tasks:
- If layered source art exists elsewhere (e.g. the original design file), bring it in and run it
  through Icon Composer to produce the `.icon` asset.
- If it doesn't exist, this is new design work (separating the mark into layers) before it's an
  Xcode task at all — worth confirming with whoever did the original artwork before scoping time.

**Navigation container.** `LinkCollector/ContentView.swift:21` wraps the `NavigationSplitView` in
a bare `VStack`. That fights edge-to-edge layout and safe-area handling under Liquid Glass — the
`VStack` doesn't do anything useful here since `NavigationSplitView` already fills the space; it
should be removed.

**Concrete glass-readiness cleanup**, once compiling against the new SDK:
- `LinkDetailView.swift`: hardcoded `.shadow(color: .gray, radius: 1.0)` on the `WebView`, and
  `.foregroundColor(.blue)` on all three header buttons (`openInBrowser`, `note`, `editLinkView`)
  — these fight the system's automatic glass/tint styling. Prefer `.tint(.blue)` or letting the
  system style win, and reconsider the shadow.
- The tags `List` in `LinkDetailView.tagsView` uses a fixed-height frame
  (`bodyTextHeight * CGFloat(self.tags.count)`) — worth a pass to confirm it still lays out
  correctly with glass-effect list backgrounds.
- Check `Views/Labels/` for any hardcoded background colors (not yet inspected in this pass).

### 2. Stay NavigationSplitView or switch to TabView

The sidebar (`LinkCollectorMenu.allCases` in `ContentView.swift`) has exactly two items: Links and
Tags. That's thin for a `NavigationSplitView` sidebar on iPhone, and iOS 26's platform direction
favors an adaptive `TabView` (sidebar-adaptable style) that presents as tabs on iPhone and morphs
into a sidebar on iPad/Mac automatically — which would also pick up Liquid Glass tab-bar styling
for free.

Shape of the change, if pursued: `TabView` replaces only the current first column (the menu
picker); each tab (Links, Tags) still needs its own List → Detail push navigation inside it, so
`LinkListView`/`TagListView` and the `selectedLink`/`selectedTag` state largely carry over.
`selectedMenu` already being a `LinkCollectorMenu` enum makes the swap mechanically small.

**Open question to settle before starting:** is Links/Tags expected to stay a fixed two-item set,
or is a third top-level section (e.g. a future "Search" or "Recent" tab) plausible? Two sections
long-term is a legitimate reason to keep `NavigationSplitView` as-is; three or more tips the
balance toward `TabView`. Recommend deciding this before touching code, since it changes the
target shape rather than just the effort.

### 3. Apple Intelligence — summarize the content of the link

This is more than a model call — the real gap is that nothing in the app currently extracts page
*body* text. `ViewModel/HTMLParser.swift` (actor-based, uses SwiftSoup) only ever populates
`title` and `ogTitle`; there's no plain-text extraction path to feed a summarizer.

Plan:
- Extend `HTMLParser` with a body-text extraction path: prefer `<article>`/`<main>`, strip
  `<script>`/`<style>`/`<nav>`, fall back to full-body text. Alternative: evaluate JS in the
  `WKWebView` already shown in `LinkDetailView`/`WebView.swift` to pull `innerText` after render,
  which handles JS-rendered pages the SwiftSoup path can't.
- Call the on-device Foundation Models framework (`LanguageModelSession`, iOS 26+) with the
  extracted text. Confirm the actual context-window limit before implementation and plan
  truncation or a chunk-then-combine strategy for long articles — don't assume a single-shot call
  works for arbitrary page length.
- Gate on both model availability and device eligibility (`SystemLanguageModel.availability`),
  with a real fallback path when unavailable — `og:description`, which `HTMLParser` is already
  positioned to read from the same meta tags it uses for `ogTitle`, is a free fallback rather than
  showing nothing.
- Run summarization **in-app, on demand** (e.g. a button in `LinkDetailView`), not inside
  `LinkPilerShareExtension` — share extensions have tight memory limits and summarization work
  doesn't belong there.
- **Schema change:** add one optional `summary: String?` attribute to `LinkEntity` in
  `LinkCollector 2.xcdatamodel` (the active model version, confirmed via `.xccurrentversion`).
  It's CloudKit-safe the same way `favicon`/`title` already are — optional, no default-value
  requirement issue. Do this migration before the SwiftData work (#5) so that migration deals with
  the final shape of the schema instead of two schema changes back to back.

### 4. Swift 6 language mode + exploit concurrency further

Worth calling out up front: this isn't a greenfield concurrency migration. `SWIFT_STRICT_CONCURRENCY
= complete` is **already turned on** (under Swift 5 language mode) for `LinkPiler`,
`LinkPilerShareExtension`, and `LinkPilerWidgetExtension`, and the code already reflects that —
`LinkCollectorViewModel` and `AppDelegate` are `@MainActor` classes, background work is already
split into actors (`HTMLParser`, `SearchHelper`, `LinkCollectorDownloader`), and
`SearchAttributeSet`/`PersistenceHelper` are explicitly `Sendable`. So this is a completion pass
and a modernization pass, not a rewrite.

**Gap found:** `LinkPilerShareExtensionMac`'s build settings are missing
`SWIFT_STRICT_CONCURRENCY = complete` (it only has `SWIFT_VERSION = 5.0`) — every other target has
it. That's the one target that hasn't actually been checked yet. Turn strict checking on there
*first*, under Swift 5, and fix whatever it surfaces — that isolates "new Mac-extension-specific
concurrency bugs" from "Swift 6 language-mode diagnostics" instead of hitting both at once.

**Sequence for the language-mode flip itself:**
1. Fix the `LinkPilerShareExtensionMac` gap above; confirm all five build config groups
   (`LinkPiler`, `LinkPilerShareExtension`, `LinkPilerShareExtensionMac`, `LinkPilerWidgetExtension`,
   and the stale project-level default) show a clean build under `-strict-concurrency=complete`.
2. Flip `SWIFT_VERSION` to 6 across all four targets (plus the project-level default, for
   consistency with the deployment-target cleanup in item #1). Given step 1, expect this to mostly
   surface Swift 6-only diagnostics — global/static mutable state, `Sendable` conformance holes
   Swift 5 didn't check — rather than new actor-isolation errors, since those are already handled.
3. Confirm the `PersistenceSwift` package (external, pinned to 0.2.15) itself builds clean under
   Swift 6 caller-side checking; if it predates its own strict-concurrency adoption, that's a
   package-level fix, same shared-package caveat as in the SwiftData section below.

**Concrete cleanup once compiling under Swift 6**, found while reading the code for this plan:
- `HTMLParser.swift` carries **two APIs for the same job**: an unused completion-handler
  `parse(url:html:completionHandler:)` (line 25) plus its private helper `findYouTubeTitle`
  (line 134), sitting alongside the `async` `parse(url:html:)` that's the one actually called
  (from `LinkCollectorViewModel.swift:276`). Grepped the whole app — nothing calls the
  completion-handler versions. Delete them; this is dead code, not something to "migrate."
- `LinkCollectorViewModel.swift` has four `DispatchQueue.main.async` / `.asyncAfter` calls
  (lines 219, 223, 415, 428) inside a class that's already `@MainActor` — they're redundant hops
  now. Replace with direct calls, or `Task { @MainActor in ... }` for the one that needs the 0.5s
  delay (`asyncAfter` → `Task { try? await Task.sleep(for: .seconds(0.5)); ... }`).
- Three `@preconcurrency` bridges exist because the protocols/imports they wrap predate Sendable
  annotations: `CLLocationManagerDelegate` (`LinkCollectorViewModel.swift:529`),
  `UNUserNotificationCenterDelegate` (`AppDelegate.swift:232`), and `import Persistence`
  (`PersistenceHelper.swift:11`). Check whether the iOS 26 SDK and the current `PersistenceSwift`
  release have picked up proper `Sendable` annotations now — if so, dropping `@preconcurrency`
  there is real, verifiable modernization rather than a no-op flag flip. If not, they should stay;
  don't strip them speculatively.
- `LinkPilerWidget/Provider.swift` implements `TimelineProvider`, whose three required methods
  (`placeholder`, `getSnapshot(in:completion:)`, `getTimeline(in:completion:)`) are still
  completion-handler-shaped in WidgetKit as of this writing — confirm whether `AppIntentTimelineProvider`
  or an async-friendly variant is worth adopting instead, since that's the one remaining
  completion-handler surface that isn't dead code and isn't obviously replaceable by app-level
  changes alone.
- `changedPeristentContext` (`LinkCollectorViewModel.swift:32`, note the existing typo — leave the
  typo alone unless renaming it is explicitly in scope, since it's a stored `@Published` Combine
  publisher referenced elsewhere) uses `.debounce`/`.receive(on: DispatchQueue.main)` Combine
  operators. These aren't broken under Swift 6, just worth a look if/when `LinkCollectorViewModel`
  moves to `@Observable` as part of the SwiftData migration below — Combine-to-`AsyncSequence`
  conversion is a natural companion then, not before.

**Explicitly not required for Swift 6 itself** (would be scope creep on this item, called out so
it doesn't get bundled in): converting `LinkCollectorViewModel` from `ObservableObject`/`@Published`
to `@Observable`. Swift 6 language mode and `@Observable` are independent axes — the former is a
compiler-mode change, the latter is a data-flow rewrite best done together with the `@Query`
switch in the SwiftData item below, not here.

### 5. Migration to SwiftData

The biggest unknown here isn't SwiftData itself — the model (`LinkEntity`/`TagEntity`, all-optional
attributes, inverse relationships, CloudKit-backed) is already in the shape SwiftData + CloudKit
wants. The real complexity is everything *around* persistence:

- **Persistence lives in an external, shared package** —
  [PersistenceSwift](https://github.com/jaeseung16/PersistenceSwift) 0.2.15 — consumed by
  `LinkCollector/ViewModel/PersistenceHelper.swift` and used across the app, share extension
  (+ Mac variant), and widget extension targets via `@preconcurrency import Persistence`. This
  isn't a local refactor: either the shared package grows a SwiftData-based implementation that
  every consuming app opts into, or this app forks off it. Decide which before scoping effort,
  since it changes whether this is a LinkPiler-only change or a package-level one affecting your
  other apps too.
- **Spotlight indexing has no confirmed SwiftData equivalent.** `PersistenceHelper.getSpotlightDelegate<T: NSCoreDataCoreSpotlightDelegate>()`
  and `LinkSpotlightDelegate.swift` currently ride on Core Data's `NSCoreDataCoreSpotlightDelegate`.
  Verify what SwiftData actually offers here — if there's no first-class equivalent, the fallback
  is manual `CSSearchableIndex` maintenance, which is real extra work and the item most likely to
  turn this from a week-scale task into a month-scale one.
- **App Group / multi-target access**: confirm SwiftData's `ModelConfiguration` can open the
  existing CloudKit-backed store in place (matching entity/attribute names, shared container URL)
  rather than requiring a one-time copy-migration that the widget and share extensions would also
  need to coordinate around.
- **Swift 6 should already be done by this point** (item #4) — do the language-mode flip on the
  Core Data code first, so this migration isn't debugging two changes at once.
- Switching the ~600-line `LinkCollectorViewModel` from `ObservableObject`/`@Published` to
  `@Observable`, and its consumers from `@EnvironmentObject` to `@Environment`, is a natural
  companion to `@Query` here — but keep it as an explicit follow-up PR, not bundled into the same
  change as the store migration itself. Two large mechanical changes in one diff is how this
  becomes unreviewable.
