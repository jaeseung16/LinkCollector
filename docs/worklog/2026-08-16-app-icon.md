# 2026-08-16 — Liquid Glass app icon

## What was done

Adopted the Icon Composer icon from `~/Documents/2026/LinkPiler/AppIcon_iOS26.icon` as the app icon.

- Copied the bundle into the repo as `LinkCollector/AppIcon_iOS26.icon` (3 layer PNGs + `icon.json`; `supported-platforms` = squares "shared", so it covers iOS, iPadOS, and macOS).
- Registered it in `LinkPiler.xcodeproj/project.pbxproj`: `PBXFileReference` with `lastKnownFileType = folder.iconcomposer.icon`, added to the `LinkCollector` group and to the **LinkPiler** app target's Resources build phase.
- Changed `ASSETCATALOG_COMPILER_APPICON_NAME` from `AppIcon` to `AppIcon_iOS26` in the app target's Debug and Release configurations.

## Which targets got it

Only the **LinkPiler** app target. Icon Composer icons apply to app targets; the three extension targets
(`LinkPilerShareExtension`, `LinkPilerShareExtensionMac`, `LinkPilerWidgetExtension`) have no
`ASSETCATALOG_COMPILER_APPICON_NAME` and do not carry app icons — the widget and the iOS share extension
present the host app's icon.

## Verification

- `xcodebuild -destination 'platform=macOS' build` — BUILD SUCCEEDED. Built app has
  `CFBundleIconName = AppIcon_iOS26`, `AppIcon_iOS26.icns`, and an `IconImageStack` (the layered
  Liquid Glass rendition) in `Assets.car`.
- `xcodebuild -destination 'platform=iOS Simulator,name=iPhone 17' build` — BUILD SUCCEEDED, with
  `CFBundleIcons`/`CFBundleIcons~ipad` pointing at `AppIcon_iOS26` and an `IconImageStack` in `Assets.car`.
- No actool warnings or errors.

## Left alone (possible follow-ups)

- The legacy `LinkCollector/Assets.xcassets/AppIcon.appiconset` is still present and still compiled into the
  bundle, just no longer referenced as the app icon. Deleting it is safe (deployment targets are iOS 26 /
  macOS 26) and would shrink the bundle slightly.
- `LinkPilerShareExtensionMac` still ships its own hand-made `icon.icns` (`CFBundleIconFile = icon`) for the
  macOS share menu; it was not regenerated from the new artwork.

# 2026-08-16 — Launch crash on `.NSPersistentStoreRemoteChange` (unrelated to the icon)

## Symptom

`EXC_BREAKPOINT` on a background thread shortly after launch, inside
`_dispatch_assert_queue_fail` ("BUG IN CLIENT OF LIBDISPATCH: Block was not expected to
execute on queue").

## Diagnosis

From the crash report (`~/Library/Logs/DiagnosticReports/LinkPiler-2026-08-16-113532.000.ips`),
the faulting thread's queue was
`com.apple.coredata.NSPersistentStoreRemoteChangeNotification...queue` and the stack was:

```
_dispatch_assert_queue_fail
dispatch_assert_queue
_swift_task_checkIsolatedSwift
swift_task_isCurrentExecutorWithFlagsImpl
closure #1 in LinkCollectorViewModel.init(persistence:)   <-- LinkCollectorViewModel.swift
Subscribers.Sink.receive(_:)
...
-[NSPersistentStoreCoordinator _postStoreRemoteChangeNotificationsForStore:andState:]
```

`LinkCollectorViewModel` is `@MainActor`, and Combine's `sink` closure is not `@Sendable`, so the
closure inherits main-actor isolation. Core Data posts `.NSPersistentStoreRemoteChange` on its own
private queue, so under Swift 6 the runtime executor check (`swift_task_isCurrentExecutor`) ran off
the main queue and trapped. The subscription had no `.receive(on:)` hop — unlike the two
subscriptions created just below it, which both already hop to main.

## Fix

`LinkCollector/ViewModel/LinkCollectorViewModel.swift` — added the missing main-queue hop:

```swift
NotificationCenter.default
  .publisher(for: .NSPersistentStoreRemoteChange)
  .receive(on: DispatchQueue.main)      // added
  .sink { self.fetchUpdates($0) }
  .store(in: &subscriptions)
```

## Verification

- iOS Simulator and macOS builds both succeed, no new warnings.
- Installed and launched on the iPhone 17 simulator (iOS 26.2): the app reaches the **Links** screen
  and stays alive past 40 s with no new crash report. Previously it trapped within seconds.

## Note

The recurring `ExcUserFault_LinkPilerWidgetExtension-*.ips` reports are an XPC misuse fault entirely
inside Apple's BoardServices/BaseBoard frameworks (`_BSBundleIDForXPCConnectionAndIKnowWhatImDoingISwear`)
with no app code on the stack — system noise, not a crash in this project's code.
